## 目的と依頼範囲

複数PC・複数Slackアプリとして稼働するZeroちゃん全員について、次の情報をWebページで確認できるようにする。

- 最新の稼働状況。
- 最後にタスクを受け付けた時刻。
- 今、新しい依頼に着手できるか。
- 作業中なら、その目的と現在段階の分かりやすい要約。生ログは表示しない。
- 共通パスワードによるログイン。

初版は閲覧専用。ページからの停止・再起動・タスク投入・担当移譲は対象外。AIの表示名はZeroちゃん固定ではなく、登録されたSlackアプリ名を使う。

## 明示承認の記録

1. 個別メールアドレス・パスワード案に対し、ユーザーは「一律のパスワードだけで良くないかい？その他はいい」と回答。
2. 共通パスワードのサーバー側検証、ログイン維持、未ログイン時のデータ取得禁止、連続失敗制限、送信者認証との分離を説明し、ユーザーは「では進めて」と回答。
3. ログイン入口と稼働一覧の画像を提示し、Macの`open`で2枚を開いた。ユーザーは「OK、レイアウトとかはいい」と回答。
4. プロジェクト名について、起動元フォルダ名を既定にし、任意の表示名、PC名での区別、フルパス非送信、作業対象リポジトリは要約で補足する案を説明。ユーザーは「OK、それでいいと思う」と回答。
5. 文書化後の保留を経て、ユーザーの「稼働状況画面の実装に戻って」で実装を再開した。

UI/UX分類は重要な視覚GUI変更。承認対象は下記の入口・一覧と表示契約。画面案はprimary Codex作成のfrontend-only試作で、実認証・実データとは未接続。

## プロジェクトの判定

- Zeroちゃんに紐づいた起動元プロジェクトフォルダを基準にする。フォルダ内の1リポジトリを勝手にプロジェクト全体とみなさない。
- 表示名の既定はフォルダbasename。例: `/Users/example/dev/bsb` → `bsb`。
- 任意の分かりやすい表示名を設定できる。設定経路は既存CLIとの整合を見て決める。
- 同名フォルダはPCの表示名と合わせて区別。表示文字列を識別子として使わない。
- フルパスをクラウドへ送信しない。PC名も任意の表示ラベルを使い、OSユーザー名等を自動公開しない。
- 実際に作業しているリポジトリは必要に応じて作業要約へ補足する。

## 推奨構成

Cloudflare Pages + 既存Supabaseを基本とする。共通パスワードの認証・保護されたデータ取得にはPages Functions等のサーバー側処理を使う。Railway常駐サーバーは初版に不要と判断。

- 各PC: 既存ローカルキュー・接続状態から監視用snapshotを作成して送信。
- Supabase: 引き継ぎとは別の稼働データと登録済みインスタンス一覧。
- Web: 共通パスワードでログイン後、保護された読み取り経路で一覧を取得。
- 共通パスワードをフロントのJSへ埋め込まない。サーバーで検証し、期限付きの安全なセッションcookie、HTTPS、ログアウト、連続失敗制限を実装する。
- 閲覧用パスワードとPCの状態送信権限を分離。閲覧者からの状態変更は禁止。
- ブラウザへ管理キーや送信者の秘密を渡さない。未認証のAPI直アクセスでもデータが返らないことを検証する。
- 既存のworker用Supabaseアカウントを閲覧者として転用しない。引き継ぎRPCやStorageの権限をページへ持ち込まない。
- 共通パスワードの変更・セッション失効の仕組みを用意する。秘密はGitやこの文書へ記載しない。

各PCには状態送信対応版の導入と初回認証・登録が必要。ローカルにしか登録されていない別PCのSlackアプリを、ページだけで自動発見できるとは説明しない。登録済みだが未通信のインスタンスも一覧に残す。

## 状態・時刻・要約の契約

- 基本は約30秒間隔のheartbeatと重要な状態変化時の送信。Webは自動取得。
- サーバー受信時刻で情報の鮮度を判定。例として90秒無通信なら状態不明。閾値は実装時にテストで固定。
- 接続状況、runner健全性、実行中件数、待ち件数、利用上限、更新待ち、承認待ちを区別する。
- 新規着手可能かはスケジューラの実条件に合わせる。単にrunning=0やプロセス存在だけで判定しない。
- 最後の依頼受付はタスク開始やheartbeatとは別。受理した新規依頼・続きの指示を対象とし、Slack再配信は重複計上しない。
- PCの固定installation ID、Slack workspace/App ID、起動世代、送信sequenceを使い、表示名の変更、再起動、送信順序逆転で混同しない。
- 同じSlackアプリの別PC同時稼働を最終書込勝ちで隠さず、重複稼働として扱う。
- ブラウザ自体がデータを取得できない場合も明示し、最後に取得した状態を最新と偽らない。
- メインCodexが節目に出す「作業目的＋現在段階」の短いユーザー向け要約を利用。heartbeatや閲覧のたびにLLMを呼ばない。
- 生ログ・依頼全文・添付・認証情報・フルパスをそのまま送信しない。要約生成は完全な秘密検出の保証ではないため、入力範囲と公開範囲を限定する。
- 要約が生成できなくてもheartbeatを継続し、「作業中・要約更新待ち」等の正直な表示にする。古い別タスクの要約を新タスクへ流用しない。
- 監視送信は有限timeout、backoff、最新snapshotへの集約。無制限にheartbeatを蓄積しない。
- **監視用DB・ネットワーク・要約・Webの障害を、Zeroちゃん本体の作業停止条件にしない。**
- 監視上の状態から自動停止・担当移譲などの制御を実行しない。
