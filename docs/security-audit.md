# Slack セキュリティ検査

ゼロちゃん宛てに「セキュリティチェックして」と投稿すると、通常の開発セッションとは別の検査フローになります。既存の開発用 AGENTS.md を読み込まない専用 Codex がコードを評価し、ホストが検査ツールを順番に実行します。コード修正、依存更新、修復ループ、Git commit は行いません。

全工程が成功・指摘あり・検査不能・失敗・中断のいずれかになった後、`レポート_YYYY-MM-DD.md` とサマリーを元の Slack スレッドへ送ります。検査不能を「脆弱性なし」と扱いません。「上のレポートの内容を修正して」は通常の開発へ流れ、同じプロジェクト・スレッドの最新の完了レポート全文を渡します。別プロジェクトのレポートは渡しません。

## 実行前の利用可能チェック

本検査の前に、毎回次の順序で確認します。未設定の場合は下記の自動初期化で質問・回答保存を行ってから実行チェックへ進みます。

1. 「セキュリティ12工程が利用可能かどうかを調べています」とSlackへ投稿し、配信を確認します。
2. 12工程すべてについて設定・認証・必要な依存を調べ、ホストが用意した小さなサンプルを実行します。CodexのJSON回答、Chrome/PlaywrightのHello World、依存監査、Semgrep Codeの既知のファイル間検出、Gitleaksの既知の疑似秘密、Socketのscan作成・report取得、ZAPのコンテナ内ローカルサイト検査、レポートの生成・保存・再読込を含みます。
3. 小規模な確認がすべて通ったら、同じソーススナップショットで対象E2E・Semgrep Code・Trivy（設定済みイメージを含む）を実行します。長時間のコードレビューを始める前に、対象固有の依存不足・解析漏れ・出力障害を確認します。
4. 1工程でも利用不能なら、全工程の確認結果を`利用可能チェック_YYYY-MM-DD.md`にまとめて返し、本検査を開始しません。疑似サンプルでの検出は、本コードの脆弱性として集計しません。
5. 全工程が通った場合だけ「全工程の利用可能状態が確認できましたので、これよりセキュリティチェックを開始します」と投稿し、その配信後に下記の本検査へ進みます。

設定だけで成功扱いにはしません。開始時に検査領域の空き容量を確認し、4 GiB未満ならツール導入・検査を開始しません。この下限は大規模検査の容量保証ではありません。E2Eの依存導入は隔離コピー内でinstall scriptを無効にして行います。Node E2EのHello Worldには、選択したworkspaceと同じPlaywright版のブラウザを専用キャッシュへ用意して使います。認証が必要な対象ではホスト管理の認証GET確認も行います。macOSの検査用ディレクトリは実体パスへ統一し、Semgrepのファイル間参照とSocketのmanifest相対パスを一致させます。Socketの事前確認は疑似manifestをサービスへ送って専用scanを作成するため、API権限・利用枠が必要です。

対象実行確認の成功結果は工程1・6・7に再利用し、最終E2E（工程11）は改めて実行します。対象実行確認で停止した場合も、取得済み指摘と解析できなかった範囲を添付に残します。再開時に完了済みの対象検査を繰り返さず、中断して成否不明なE2Eも自動再実行しません。対象確認中に中断したSemgrep・Trivyは、ジョブの子プロセス回収後に未完了のローカル出力を破棄して再実行できます。事前確認は、その後の通信障害・認証失効・ディスク消費などまで保証するものではありません。本検査で失敗・検査不能・中断が残った場合は、結果を保存し「検査は未完了」と通知します。

## 実行順

1. 既存 Chrome Playwright E2E 実行と、コードに対するテスト網羅性レビュー
2. 必要なリファクタリングの指摘（変更なし）
3. ソースコードの脆弱性レビュー
4. プロンプトインジェクションのレビュー
5. 依存監査（npm / pnpm / Bun / pip-audit）
6. Semgrep Code（アカウントのCode policyとProのファイル間解析）
7. Trivy **0.69.3 固定**（ファイル、依存、構成、秘密情報、ライセンス、設定済みイメージ）
8. Gitleaks（作業スナップショットと取得可能な Git 履歴、値は伏せる）
9. Socket.dev（対応する依存 manifest を送信し、scan 完了を待つ）
10. Docker OWASP ZAP（指定された URL の範囲）
11. 最終 Chrome Playwright E2E
12. 全工程を一つのレポートへ集約

専用ツール領域へ不足する CLI を導入します。Semgrep Codeの認証とProエンジン、Socketの権限・利用枠、Dockerの稼働、Chromeの認証状態を実行で確認します。Semgrep CEへの自動切替は行いません。全言語・全ルールの無条件実行を保証するものではなく、CodeQLと完全に同じ検出範囲でもありません。既存E2E設定がない場合も明示し、検査のために製品側のテストやソースを自動作成・修正しません。

## 初回の自動初期化

初回の検査依頼でZeroちゃんが共通接続と対象repositoryを確認します。Socket組織は登録済みキーからAPIで取得し、候補が一つならそのSlackアプリ共通の設定として再利用します。複数なら同じスレッドで選択を確認します。キーを変更した場合は以前の共通組織を流用しません。明示したプロジェクト単位の組織設定は上書きしません。

対象URLと認証範囲が未設定なら、その不足分だけを同じSlackスレッドで尋ねます。例えば次のように返信します。

```text
URL: https://example.com/app
認証: 公開・未ログイン範囲
```

ログイン領域も検査する場合は次の形です。

```text
認証: ログイン後も含む
確認パス: /app/account
確認文言: ログアウト
```

設定変更権限を持つ送信者の明示的な回答を保存し、**同じ依頼から自動再開**します。再度「セキュリティチェックして」と依頼する必要はありません。回答待ちは永続化してworker枠を解放し、別スレッドの依頼を進めます。中止、重複返信、gateway/runner再起動も同じjobに結び付けます。検査開始時に設定を固定し、他の依頼で設定が変わっても実行中の対象へ混ぜません。

E2Eの入口と静的に特定できるlocalhost portはソースから取得します。URL・認証不要の判断はソースやモデルの推測から許可しません。未対応のE2E形式・不足するテストは明示し、別サービスやHello Worldの成功を本プロジェクトの検査成功として扱いません。

認証情報の登録はアプリ共通で一度だけ必要です。本人のサービス認証・権限復旧が必要な場合はその操作を案内し、キーをSlackに投稿させません。非表示入力の補助コマンドと設定確認は次のとおりです（通常のrepository初期化では手入力の設定コマンドは不要）。

```sh
zerochan security socket-token
zerochan security semgrep-token
zerochan security status
```

管理者用の `target URL`、`auth required|none`、`auth-probe PATH TEXT`、`e2e-port PORT`、`socket-org ORG`、`semgrep-repo OWNER/REPO` も残しています。

`socket-token`と`semgrep-token`は端末で非表示入力します。トークンをコマンド引数、ソース、レポートへ書かないでください。`semgrep-repo`はSemgrepの対象リポジトリ名です。未設定ならGitのoriginから取得します。Semgrep CodeでCode policyが利用できるアカウントの認証情報が必要です。CLIは`scan --config policy --pro`でローカル解析し、検出結果・ソース断片をアップロードする`semgrep ci`は使いません。ポリシー取得とProエンジン取得にはSemgrepへの通信が発生します。CodeQLは新規検査では実行せず、GitHub Code Securityの契約設定も要求しません。

ZAP は既定では passive baseline です。権限のある対象へ active scan を行う場合は `zerochan security active on` と設定します。対象 URL を変更すると active 設定は解除されます。イメージは `zerochan security image IMAGE` で追加します。隔離Trivyはレジストリから取得できるイメージを対象とし、ホストDockerにしか存在しないイメージは事前チェックで停止します。ホストのレジストリ認証情報は流用しません。URLはホスト側に保存した設定を使用します。初期化の明示的なURL回答だけを設定に反映し、通常の本文・添付・repository中のURLは検査先にしません。

Chrome の対象 URL 用 cookie をホストが取得し、ホスト管理の認証確認処理と ZAP へメモリ内で渡します。LLM、プロジェクトの設定ファイルや既存 E2E コードへは渡しません。専用 Chrome 確認は設定された認証ページへの GET のみで、他 origin・WebSocket・GET/HEAD 以外のリクエストを遮断します。認証確認用ページで指定した文字列を含む応答が確認できなければ、認証領域を検査済みと表示しません。ZAP は自身の HTTP sender 経由の応答で認証を確認し、ホストからの確認だけで成功にしません。cookie 以外の独自認証、MFA、期限切れ、全ページの認証維持は自動的に成功したものと扱いません。

## 保存・再開・範囲

- 実行工程と結果は `security-audits/<job-id>/journal.json`、公開用レポートは既存 outbox に保存します。
- ホストの制御領域と分離したソースコピーでツールを実行し、元のチェックアウトを変更しません。Gitでは追跡対象とignoreされていない未追跡ファイルを対象にし、追跡対象のローカル変更も含めます。別repository・worktree、秘密設定、生成物、symlink、巨大ファイル等の対象外一覧をレポートへ付けます。
- 旧13工程の完了レポートはそのまま再配信できます。旧13工程の途中記録は自動で12工程へ変換せず、元記録を保持して新しい検査依頼を案内します。
- 現行12工程では、再開時も新たに利用可能チェックを行います。すでに本検査を開始したジョブで再確認に失敗した場合は、取得済み工程と部分レビューを未完了レポートとして保存し、修正依頼から参照できる状態を保ちます。未完了確定を先に永続化するため、レポート保存中に再起動しても本検査へ戻りません。Socketの事前scan IDは保存してreport取得を再確認し、作成結果が不明なscanを自動で再作成しません。
- 再起動時は工程1〜4のコードレビューを保存済みの分割結果から再開します。旧版で別worktreeを含めていた場合も、元のコピーと結果の対応を保持したまま対象外にします。E2Eや工程5以降で実行途中だった検査は中断として扱い、副作用の成否が分からない操作を自動再送しません。
- 長時間の検査では、通常のジョブと同じく開始10分・30分・60分、その後1時間ごとに、現在の工程と取得済みの進捗を元のSlackスレッドへ通知します。処理単位ごとの通知はまとめられ、長いツール実行中にも現在の工程を通知します。
- Slack 添付は既存の成果物配信 checkpoint を使います。再配信で検査自体を再実行しません。利用可能チェックで停止した結果も内容のハッシュを確認して再配信し、過去の本検査レポートへの修正依頼を妨げません。
- コードレビューは全対象ファイルの分割評価です。ファイルをまたぐ意味解析の完全性を保証しません。
- コードレビューには監査専用の回答上限（1 MB）と10分の実行枠を使います。生成コードの長い1行も、指示・ファイル一覧・JSONエスケープを含む入力全体が100 KB以内になるよう追加分割し、元の分割の開始行と文字位置を保持します。失敗した分割評価だけを再試行します。分類できた一時的な通信・混雑・レート制限は30秒・60秒待機して最大2回、それ以外は最大1回再試行し、ファイル・開始行・秘匿化済みの失敗理由を残します。通常のスレッド判定の上限は変更しません。
- pnpmの監査とE2E依存導入は`packageManager`の指定版を専用ツール領域へ導入して使います。E2Eは`--frozen-lockfile`で導入し、install scriptとpnpmfile hookを実行しません。ルートの `test:e2e` / `e2e` が明示するPlaywright設定または単一のルート設定を選びます。配下に一つあるだけの設定は別サービスの可能性があるため選びません。ルートscriptが選ぶ `node entry.cjs` と `pnpm -C DIR exec node ENTRY` 等にも対応し、そのworkspaceのPlaywrightでHello Worldを確認します。任意のshell commandは実行入口にしません。独自Node runnerの本検査は終了コードと完了件数（`N checks passed` またはTAP）を確認します。
- TrivyのJSONは標準出力ではなく所有者専用ファイルへ保存し、終了コード・ファイル種別・256 MiBの上限を確認してから解析します。空出力やディスク不足をJSON構文エラーで隠しません。
- Semgrepの部分解析エラーは種類と対象ファイル・行範囲を記録し、取得済みの指摘を保持します。Gitleaksの証拠ハッシュは、stdoutではなく実際に解析したJSONを対象にします。
- macOSの検査隔離では、Javaのパス解決に必要な親ディレクトリ自身の読み取りを許可します。配下の秘密ファイルは許可せず、JVMのhome・一時領域は工程専用領域に固定します。
- ZAPは選択中のローカルDockerへ接続します。ホストのDocker認証設定は渡しません。URLにパスを指定した場合は、そのパスを巡回の開始点として維持します。
- Playwright設定形式のE2Eは工程専用の隔離領域で実行し、`channel: chrome` を指定します。Node形式は選択したworkspaceのPlaywrightと対応するChromiumを使います。macOS では `e2e-port` で指定した localhost のテスト環境だけへの通信を許可し、実認証は渡しません。独自Node runnerも同じ隔離で実行し、ホストのDocker socketは渡しません。動的portやDockerを必要とする独自runnerは、その条件を隔離内で満たせなければ検査不能として記録します。Linux の bubblewrap ではネットワークを分離するため、このローカル接続経路は未対応として記録します。スキップ、認証未確認、設定不足を明示します。

中止を依頼した場合は進行中の子プロセスを終了し、通常の中止通知を返します。途中までの工程記録は保存されますが、全工程の最終レポートとしては配信しません。

認証不要の公開アプリでは `zerochan security auth none` を指定できます。認証モードが未設定の場合や、`required`で認証確認できない場合は、利用可能チェックで停止します。

検査は既存のプロジェクトキューで順番に動きます。大きなプロジェクトの検査中は後続依頼を待たせます。完了後はソースコピー、工程別の生データ、一時ブラウザ領域を削除し、再配信に必要なレポートと工程記録を保持します。利用可能チェック用の一時コピーは確認終了時に削除します。利用可能チェックで停止した場合もソースコピーを削除し、再配信用の結果・証拠ハッシュを保持します。プロセスの終了確認が未完了な場合や、中断時の一時領域は再開時に扱います。検査後の開発依頼は新しい開発セッションで始まり、検証済みレポートを引き継ぎます。レポートが消失・改変されていた場合は内容を推測せず、必要な依頼だけ再添付を求めます。
